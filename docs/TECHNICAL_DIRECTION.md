# 技术方向草案

## 1. 运行平台

- 第一目标：Windows/macOS 桌面浏览器，键盘操作，60 FPS。
- 第二目标：移动浏览器，触控操作，稳定 30–60 FPS。
- 发布产物为静态 Web 应用，可部署到普通静态站点；开发阶段通过本地服务器运行。

## 2. 建议技术栈

- 构建：Vite。
- 语言：TypeScript，启用严格类型检查。
- 3D：Three.js，使用 ES Module，不再内嵌压缩版运行库。
- UI：语义化 HTML + CSS + 少量 TypeScript；首个垂直切片暂不引入大型 UI 框架。
- 资产：glTF 2.0 / GLB；纹理优先 WebP/KTX2，界面图标使用统一 SVG 源文件。
- 测试：核心状态与配置使用单元测试；关键流程后续加入浏览器冒烟测试。
- 存档：带版本号和迁移函数的本地存档，初期使用 `localStorage` 封装层。

具体依赖版本在 Node.js 工具链安装时锁定，并提交 lockfile，避免使用浮动的 CDN 版本。

## 3. 架构边界

```text
App
├─ Core: 时钟、渲染器、资源加载、事件总线、质量分级
├─ Game Flow: lobby → loading → running → chase → reward → result
├─ Runner: 换道、跳跃、下滑、受击、无敌、收集
├─ Pursuit: 洞洞幺距离、阶段触发、传送门逃脱
├─ World Runtime: 读取世界包，拼接路线段与动态事件
├─ Presentation: 相机、特效、音频、HUD、界面动效
└─ Persistence: 货币、藏品、设置、解锁与存档迁移
```

核心逻辑不引用“狗熊岭”“比奇堡”等具体名称或第三方资源。名称、地标、NPC、音乐、障碍和故事均由可替换世界包提供。

## 4. 首个垂直切片原则

- 使用固定三条跑道和自定义胶囊/AABB 碰撞，不在第一阶段引入完整刚体物理引擎。
- 跑酷状态使用确定的有限状态机，避免把动画、输入和碰撞写进同一更新函数。
- 场景按路线段循环复用；障碍、金币、特效使用对象池，避免运行中频繁创建对象。
- 渲染分辨率、阴影、植被密度和后期效果分级，先建立性能预算再堆画质。
- 正式角色只从经确认的 GLB 加载；代码中不提供“球体拼装角色”的后备实现。

## 5. 性能预算草案

- 桌面目标：1080p 下稳定 60 FPS，常规帧 CPU + GPU 合计不超过约 16.6 ms。
- 移动目标：按设备等级选择 30 或 60 FPS。
- 同屏可见三角形：桌面建议控制在 50–80 万以内，移动端控制在 20–35 万以内。
- 活跃绘制调用：桌面尽量低于 250，移动端尽量低于 120。
- 首屏必须资源：压缩后尽量低于 12 MB；世界内容按需加载。

这些数字是垂直切片预算，会根据实测设备调整，不是对美术质量的替代。
